Selectors & Locators στο UI Automation

HTML, CSS Selectors, XPath, Playwright Locators και Stable Automation

1. Γιατί χρειαζόμαστε Selectors και Locators

Στο UI automation πρέπει να μπορούμε να εντοπίσουμε με αξιόπιστο τρόπο τα HTML elements με τα οποία θέλουμε να αλληλεπιδράσουμε. Πριν κάνουμε click, fill, assert ή διαβάσουμε text, πρέπει πρώτα να βρούμε το σωστό element μέσα στο DOM.

Click σε κουμπί Login ή Register

Συμπλήρωση email, password ή άλλου input

Έλεγχος error message

Εύρεση συγκεκριμένης γραμμής σε table και click στο σωστό action button

2. HTML Elements, Tags και Attributes

<button id="login-button" class="primary-button"> Login </button>

Στο παράδειγμα αυτό:

button = HTML tag / element type

id="login-button" = attribute

class="primary-button" = attribute

Login = text content

<input id="email" name="email" type="email" placeholder="Enter your email" />

Attributes όπως id, name, type, placeholder και data-testid μπορούν να χρησιμοποιηθούν για τον εντοπισμό ενός element.

3. Selector vs Locator

Selector είναι η έκφραση ή ο κανόνας με τον οποίο περιγράφουμε ποιο element θέλουμε να βρούμε στο DOM.

#login-button button.primary-button input[name="email"]

Locator είναι το αντικείμενο ή API του automation framework που χρησιμοποιεί μια τέτοια πληροφορία για να βρει και να χειριστεί το element.

page.locator("#login-button"); page.getByLabel("Email"); page.getByTestId("login-button");

Mental model: Selector = πώς περιγράφω το element. Locator = πώς το automation framework το εντοπίζει και το χειρίζεται.

4. Βασικοί τρόποι εντοπισμού Elements

4.1 Stable ID

<button id="login-button">Login</button>

CSS: #login-button Playwright: page.locator("#login-button");

Ένα σταθερό, σημασιολογικό id είναι συνήθως καλή επιλογή. Δεν αρκεί όμως το element να έχει id· πρέπει το id να μην αλλάζει δυναμικά.

4.2 Class

<button class="primary-button">Login</button>

CSS: .primary-button CSS: button.primary-button

Οι classes συχνά χρησιμοποιούνται για styling και μπορεί να αλλάξουν χωρίς να αλλάξει η λειτουργία. Γι’ αυτό δεν είναι πάντα η πιο σταθερή επιλογή για automation.

4.3 Attribute Selectors

input[name="email"] input[type="email"] [data-testid="email-input"]

Μπορούμε να επιλέξουμε element με βάση οποιοδήποτε χρήσιμο attribute.

4.4 data-testid

<button data-testid="login-button">Login</button> page.getByTestId("login-button");

Το data-testid λειτουργεί ως explicit testing contract ανάμεσα στο frontend και στο automation. Μπορεί να παραμένει σταθερό ακόμα και αν αλλάξει το styling ή η DOM structure.

4.5 Text, Role και Label

page.getByText("Login"); page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Login")); page.getByLabel("Email");

Role, label και user-facing text είναι πολύ χρήσιμα επειδή περιγράφουν το element με τρόπο κοντά σε αυτό που αντιλαμβάνεται ο χρήστης.

5. CSS Selectors – πιο αναλυτικά

5.1 Combinators και σχέσεις Elements

form > input /* direct child */ form input /* descendant */ label + input /* αμέσως επόμενο sibling */ label ~ input /* επόμενο sibling σε γενικότερο επίπεδο */

Οι combinators επιτρέπουν να περιγράψουμε τη σχέση ανάμεσα σε elements.

5.2 Attribute patterns

[name="email"] [id^="user-"] /* ξεκινάει με */ [id$="-email"] /* τελειώνει με */ [class*="error"] /* περιέχει */

Αυτά είναι χρήσιμα όταν ένα attribute είναι μερικώς δυναμικό αλλά έχει σταθερό pattern.

5.3 nth-child και θέση

button:nth-child(2) page.locator("button").nth(1);

Selectors που βασίζονται στη θέση είναι πιο fragile. Χρησιμοποιούνται όταν η θέση αποτελεί πραγματικά μέρος της λειτουργίας και όχι απλώς επειδή "τυχαίνει" το element να είναι δεύτερο.

6. XPath – όταν το HTML δεν είναι automation-friendly

Το XPath είναι ιδιαίτερα χρήσιμο όταν ο frontend developer δεν έχει δώσει id, class, name, data-testid, label ή άλλο σταθερό identifier. Τότε μπορούμε να αξιοποιήσουμε το text και τις σχέσεις parent/child/sibling μέσα στο DOM.

<main> <section> <h2>Profile Settings</h2> <div> <span>Email</span> <input> </div> <div> <button>Save</button> <button>Cancel</button> </div> </section> <section> <h2>Security Settings</h2> <div> <span>New Password</span> <input> </div> <div> <button>Save</button> <button>Cancel</button> </div> </section> </main>

6.1 XPath με text

//button[normalize-space()="Save"]

Αυτό βρίσκει όλα τα Save buttons. Αν υπάρχουν περισσότερα, χρειάζεται context.

6.2 XPath με context / parent section

//section[.//h2[normalize-space()="Profile Settings"]] //button[normalize-space()="Save"]

Η πρόθεση πλέον είναι σαφής: βρες το Save που ανήκει στο Profile Settings.

6.3 XPath με sibling

//span[normalize-space()="Email"]/following-sibling::input

Βρίσκουμε το input που βρίσκεται δίπλα στο text Email.

6.4 XPath μέσω parent

//div[.//span[normalize-space()="Email"]]//input

Βρίσκουμε το div που περιέχει το Email και μέσα σε αυτό το input.

6.5 Ancestor / preceding-sibling / descendant

//span[normalize-space()="Email"]/ancestor::div[1]//input //span[normalize-space()="Email"]/preceding-sibling::input //section//button

Το XPath μπορεί να κινηθεί προς τα πάνω, προς siblings ή προς descendants και έτσι να χρησιμοποιήσει τη δομή του DOM όταν λείπουν καλά identifiers.

6.6 Exact text vs contains

//button[normalize-space()="Login"] //button[contains(normalize-space(), "Login")]

Το πρώτο ζητά ακριβές text. Το δεύτερο αρκείται στο να περιέχεται η λέξη Login.

7. Stable vs Fragile / Flaky Locators

<button>Login</button> <button>Cancel</button>

(//button)[2]

Αρχικά το δεύτερο button είναι το Cancel. Αν προστεθεί πριν από αυτά ένα νέο button, η σειρά αλλάζει και ο locator μπορεί να δείχνει αλλού.

<button>Login with Google</button> <button>Login</button> <button>Cancel</button>

Position-based selectors δεν περιγράφουν ποιο element θέλουμε· περιγράφουν ποιο element τυχαίνει να βρίσκεται σε μια θέση σήμερα.

7.1 Absolute XPath

/html/body/main/section[1]/div[4]/button[1]

Ένα absolute XPath εξαρτάται έντονα από την τρέχουσα DOM structure. Μικρές αλλαγές σε wrappers ή σειρά elements μπορούν να το σπάσουν.

7.2 Long CSS Path

body > main > section:nth-child(1) > div:nth-child(3) > input

Το ίδιο πρόβλημα υπάρχει σε μεγάλα structural CSS paths.

7.3 Dynamic IDs

<button id="button-927461">Login</button> <button id="button-483920">Login</button>

Αν το id αλλάζει σε κάθε render/session, δεν είναι stable locator. Προτιμούμε κάτι σταθερό όπως id="login-button" ή data-testid="login-button".

8. Multiple Matches και Uniqueness

Ένας καλός locator ιδανικά πρέπει να οδηγεί σε ένα συγκεκριμένο element. Αν ένας selector βρίσκει πολλά elements, πρέπει να τον κάνουμε πιο συγκεκριμένο χρησιμοποιώντας context, role, label, test id ή container.

button input[type="password"]

Οι παραπάνω selectors συχνά επιστρέφουν περισσότερα από ένα elements. Αν υπάρχουν Password και Confirm Password, το input[type="password"] δεν αρκεί.

9. Collections, Cards και Tables

<table> <tr data-testid="user-row"> <td>Maria</td><td>maria@test.com</td><td><button>Delete</button></td> </tr> <tr data-testid="user-row"> <td>Nikos</td><td>nikos@test.com</td><td><button>Delete</button></td> </tr> </table>

Κακό mental model: "πάρε το δεύτερο Delete button". Καλύτερο: βρες πρώτα τη γραμμή του συγκεκριμένου user και μετά το Delete μέσα σε αυτή.

//tr[.//td[normalize-space()="nikos@test.com"]] //button[normalize-space()="Delete"]

Locator row = page.getByTestId("user-row") .filter(new Locator.FilterOptions().setHasText("nikos@test.com")); row.getByRole(AriaRole.BUTTON, new Locator.GetByRoleOptions().setName("Delete")).click();

12. Iframes

Αν ένα element βρίσκεται μέσα σε iframe, δεν το εντοπίζουμε κατευθείαν από το main page DOM. Πρέπει να στοχεύσουμε πρώτα το frame και μετά το element μέσα σε αυτό.

page.frameLocator("#payment-frame") .getByLabel("Card number") .fill("4111111111111111");

13. Πρακτική προτεραιότητα επιλογής Locator

Role / Label / user-facing semantics, όταν είναι διαθέσιμα και σταθερά.

data-testid ή άλλο explicit testing attribute.

Stable semantic id ή άλλο σταθερό attribute.

Simple CSS selector.

Relative XPath με meaningful context.

Position-based nth/index μόνο όταν η θέση έχει πραγματική σημασία.

Absolute XPath ή μεγάλα structural CSS/XPath paths ως τελευταία λύση.

15. Shadow DOM

Ορισμένα web components χρησιμοποιούν Shadow DOM, δηλαδή ξεχωριστό DOM boundary. Τα σύγχρονα automation frameworks μπορούν συχνά να το χειριστούν, αλλά πρέπει να γνωρίζουμε ότι το element μπορεί να μην βρίσκεται στο συνηθισμένο DOM tree όπως ένα απλό element.

15.1 Τι είναι το Shadow DOM

Στο κανονικό DOM ένα button μπορεί να βρίσκεται απευθείας μέσα σε ένα div. Με το Shadow DOM, ένα custom element μπορεί να έχει δικό του εσωτερικό DOM, απομονωμένο από την υπόλοιπη δομή της σελίδας.

<div> <button>Login</button> </div>

Στο κανονικό DOM το Playwright εντοπίζει το Login button με έναν συνηθισμένο locator.

await page.getByRole('button', { name: 'Login' }).click();

15.2 Custom element και Shadow Root

Ένα web component μπορεί να εμφανίζεται στη σελίδα ως custom HTML element.

<login-component></login-component>

Στα Chrome DevTools η εσωτερική δομή του μπορεί να εμφανίζεται ως εξής. Η ένδειξη #shadow-root (open) είναι αναπαράσταση των DevTools και όχι πραγματικό HTML tag.

<login-component> #shadow-root (open) <button>Login</button> </login-component>

15.3 Playwright TypeScript – Click μέσα σε Open Shadow DOM

Το Playwright υποστηρίζει το open Shadow DOM με τους συνηθισμένους locators. Μπορούμε να περιορίσουμε την αναζήτηση στο συγκεκριμένο web component.

await page.locator('login-component') .getByRole('button', { name: 'Login' }) .click();

Δεν χρειάζεται frameLocator(), γιατί το Shadow DOM δεν είναι iframe.

15.4 Playwright TypeScript – Συμπλήρωση φόρμας μέσα σε Shadow DOM

Φαντάσου ένα custom component με ένα input και ένα κουμπί Search μέσα στο open Shadow DOM του.

<search-component> #shadow-root (open) <label for="search">Search</label> <input id="search" type="text"> <button>Search</button> </search-component>

Εντοπίζουμε πρώτα το component και μετά αλληλεπιδρούμε με τα εσωτερικά elements χρησιμοποιώντας Playwright TypeScript.

const search = page.locator('search-component'); await search.getByRole('textbox', { name: 'Search' }) .fill('Playwright'); await search.getByRole('button', { name: 'Search' }) .click();

15.5 Open και Closed Shadow DOM

Open Shadow DOM: οι Playwright locators μπορούν να εντοπίζουν τα εσωτερικά elements. Closed Shadow DOM: δεν υποστηρίζεται η κανονική πρόσβαση στα εσωτερικά elements μέσω Playwright locators.

15.6 Shadow DOM vs iframe

iframe = ξεχωριστό HTML document ενσωματωμένο σε μια σελίδα. Shadow DOM = εσωτερικό DOM ενός web component στην ίδια σελίδα. Για iframe χρησιμοποιούμε frameLocator(). Για open Shadow DOM χρησιμοποιούμε κανονικούς locators.

iframe: await page.frameLocator('#payment-frame') .getByLabel('Card number') .fill('4111111111111111'); open Shadow DOM: await page.locator('login-component') .getByRole('button', { name: 'Login' }) .click();

15.7 Πρακτικό συμπέρασμα

Αν δεις #shadow-root (open) στα DevTools, ξέρεις ότι το element ανήκει σε Shadow DOM. Στο Playwright μπορείς συνήθως να συνεχίσεις με getByRole(), getByLabel() ή locator() όπως σε ένα κανονικό element, αρκεί το Shadow DOM να είναι open.

16. Βασικό Συμπέρασμα

Ο στόχος δεν είναι απλώς να βρούμε έναν selector που δουλεύει σήμερα. Θέλουμε locator που περιγράφει την πραγματική ταυτότητα του element και παραμένει αξιόπιστος όταν αλλάζει άσχετα το styling ή η DOM structure. Καλός locator είναι σταθερός, συγκεκριμένος και συνδεδεμένος με τη σημασία του element· fragile locator είναι αυτός που βασίζεται κυρίως σε σειρά, generated id, styling class ή μακρύ structural path.
