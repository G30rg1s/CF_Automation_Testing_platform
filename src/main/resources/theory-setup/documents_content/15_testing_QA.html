Automation Testing – Questions & Answers

1. Πότε είναι κατάλληλη η αυτοματοποίηση ενός test;

Ένα test είναι κατάλληλο για αυτοματοποίηση όταν εκτελείται συχνά, έχει σαφές αναμενόμενο αποτέλεσμα και η λειτουργία που ελέγχει είναι σχετικά σταθερή. Ιδιαίτερα χρήσιμα είναι τα επαναλαμβανόμενα Regression Tests, τα Smoke Tests και οι έλεγχοι που πρέπει να εκτελεστούν με πολλά διαφορετικά δεδομένα. Εξετάζουμε επίσης πόσο χρόνο εξοικονομεί η αυτοματοποίηση σε σχέση με το κόστος ανάπτυξης και συντήρησης του test.

Παράδειγμα: Μετά από κάθε αλλαγή στον κώδικα, εκτελούμε αυτόματα ένα test που συνδέεται με έγκυρα στοιχεία χρήστη και επιβεβαιώνει ότι εμφανίζεται η αρχική σελίδα. Επειδή το ίδιο σενάριο επαναλαμβάνεται σε κάθε release, αξίζει να αυτοματοποιηθεί.

2. Πότε πρέπει να αποφεύγουμε το Automated Testing;

Δεν συμφέρει να αυτοματοποιούμε κάθε έλεγχο. Όταν η διεπαφή αλλάζει καθημερινά, τα scripts μπορεί να χρειάζονται συνεχείς διορθώσεις. Επίσης, το Exploratory Testing απαιτεί παρατήρηση, πειραματισμό και ανθρώπινη κρίση, ενώ στο Usability Testing μας ενδιαφέρει πώς βιώνει ο χρήστης την εφαρμογή. Ένα προσωρινό ή μοναδικό σενάριο ενδέχεται να είναι γρηγορότερο να ελεγχθεί χειροκίνητα.

Παράδειγμα: Αν σχεδιάζεται ακόμη η τελική μορφή μιας φόρμας, η δημιουργία δεκάδων UI tests για κουμπιά που αλλάζουν συνεχώς θέση μπορεί να οδηγήσει σε άσκοπη συντήρηση. Μπορούμε όμως να αυτοματοποιήσουμε νωρίτερα σταθερούς ελέγχους στο API.

3. Ποια χαρακτηριστικά εξετάζουμε σε ένα Test Automation Framework;

Η επιλογή ενός framework πρέπει να βασίζεται στις πραγματικές ανάγκες του project. Εξετάζουμε αν είναι code-based ή codeless, open-source ή commercial, ποιες γλώσσες προγραμματισμού υποστηρίζει και αν συνεργάζεται με τους browsers, τα λειτουργικά συστήματα και τις τεχνολογίες που χρησιμοποιούμε. Σημαντικές είναι επίσης η ευκολία εκμάθησης, η τεκμηρίωση, η κοινότητα ή η τεχνική υποστήριξη, η συντηρησιμότητα των tests, η δυνατότητα παράλληλης εκτέλεσης, το reporting, η ενσωμάτωση με CI/CD και το συνολικό κόστος.

Παράδειγμα: Μια ομάδα που αναπτύσσει web εφαρμογή με Java μπορεί να προτιμήσει Selenium WebDriver με JUnit ή TestNG, ενώ μια ομάδα που επιθυμεί σενάρια σε πιο περιγραφική μορφή μπορεί να εξετάσει Robot Framework. Κανένα εργαλείο δεν είναι καλύτερο για κάθε περίπτωση.

4. Πρέπει να αυτοματοποιούμε όλα τα tests;

Όχι. Η αυτοματοποίηση είναι μέσο βελτίωσης της ποιότητας και όχι αυτοσκοπός. Τα επαναλαμβανόμενα και προβλέψιμα tests προσφέρουν συνήθως μεγαλύτερο όφελος, ενώ οι διερευνητικοί έλεγχοι, οι αξιολογήσεις ευχρηστίας και ορισμένες οπτικές ή προσβασιμότητας δοκιμές χρειάζονται ανθρώπινη συμμετοχή. Η καλύτερη στρατηγική συνδυάζει Manual και Automated Testing, με βάση τον κίνδυνο που καλύπτει κάθε έλεγχος.

Παράδειγμα: Αυτοματοποιούμε το login με σωστό και λάθος password, αλλά ζητάμε από πραγματικούς χρήστες να αξιολογήσουν αν τα μηνύματα σφάλματος είναι εύκολα κατανοητά.

5. Τι είναι το Test Environment;

Το Test Environment είναι ο συνδυασμός υποδομών και ρυθμίσεων όπου εκτελείται η δοκιμαστική εφαρμογή: λειτουργικό σύστημα, έκδοση εφαρμογής, βάση δεδομένων, browser, εξαρτήσεις, υπηρεσίες, δίκτυο και κατάλληλα test data. Πρέπει να είναι ελεγχόμενο και αναπαραγώγιμο, ώστε τα αποτελέσματα των tests να είναι αξιόπιστα. Όπου χρειάζεται, προσομοιάζει το Production Environment, χωρίς να χρησιμοποιούμε απρόσεκτα πραγματικά προσωπικά δεδομένα.

Παράδειγμα: Μια εφαρμογή που χρησιμοποιεί MySQL και Kafka μπορεί να δοκιμάζεται τοπικά με Docker Compose, ώστε όλοι οι testers να εκτελούν τα tests με αντίστοιχες υπηρεσίες.

6. Τι είναι το Browser Automation;

Το Browser Automation επιτρέπει σε ένα πρόγραμμα να ελέγχει αυτόματα έναν browser: να ανοίγει σελίδες, να συμπληρώνει φόρμες, να πατά κουμπιά, να διαβάζει στοιχεία της οθόνης και να επαληθεύει αποτελέσματα. Εργαλεία όπως Selenium και Playwright χρησιμοποιούνται για τέτοιους ελέγχους. Ένα σωστό test περιλαμβάνει ενέργειες και assertions, όχι μόνο αυτοματοποιημένα clicks.

Παράδειγμα: Το test ανοίγει τη φόρμα login, εισάγει στοιχεία, πατά «Σύνδεση» και ελέγχει ότι εμφανίζεται το όνομα χρήστη. Αν εμφανιστεί μήνυμα λάθους, το test αποτυγχάνει.

7. Τι είναι το Cross-Browser Testing;

Το Cross-Browser Testing ελέγχει αν μια web εφαρμογή λειτουργεί σωστά σε διαφορετικούς browsers, όπως Chrome, Firefox, Safari και Edge. Μπορεί επίσης να καλύπτει διαφορετικές εκδόσεις, λειτουργικά συστήματα και μεγέθη οθόνης. Δεν μας ενδιαφέρει απαραίτητα η απόλυτα πανομοιότυπη εμφάνιση, αλλά η σωστή λειτουργία, η αναγνωσιμότητα και η συνεπής εμπειρία χρήσης.

Παράδειγμα: Ελέγχουμε αν το ίδιο dropdown ανοίγει κανονικά και αν η φόρμα αποθηκεύεται τόσο στον Chrome όσο και στον Firefox.

8. Γιατί είναι απαραίτητο το Cross-Browser Testing;

Οι browsers χρησιμοποιούν διαφορετικές μηχανές απόδοσης και μπορεί να διαφέρουν στον χειρισμό CSS, JavaScript και συγκεκριμένων Web APIs. Ένα χαρακτηριστικό που λειτουργεί σε έναν browser ενδέχεται να εμφανίζεται ή να συμπεριφέρεται διαφορετικά σε άλλον. Το Cross-Browser Testing μειώνει τέτοια προβλήματα και βοηθά να καλυφθούν οι browsers που χρησιμοποιούν πραγματικά οι πελάτες.

Παράδειγμα: Μια ημερομηνία σε HTML φόρμα μπορεί να εμφανίζεται διαφορετικά ανά browser. Ελέγχουμε ότι η επιλεγμένη τιμή αποθηκεύεται σωστά, ανεξάρτητα από τη μορφή του date picker.

9. Τι είναι το Automated Regression Testing;

Το Automated Regression Testing είναι η αυτόματη επανεκτέλεση ελέγχων παλιότερων λειτουργιών μετά από αλλαγές στον κώδικα, στις εξαρτήσεις ή στις ρυθμίσεις. Στόχος είναι να εντοπίζονται γρήγορα regressions, δηλαδή προβλήματα που εμφανίστηκαν σε λειτουργίες οι οποίες προηγουμένως δούλευαν σωστά. Δεν αποδεικνύει ότι η εφαρμογή δεν έχει κανένα bug· ελέγχει όσα σενάρια περιλαμβάνει η test suite.

Παράδειγμα: Προσθέτουμε νέο τρόπο πληρωμής και εκτελούμε ξανά τα υπάρχοντα tests για σύνδεση χρήστη, καλάθι, checkout και έκδοση απόδειξης.

10. Ποιες είναι οι καλύτερες πρακτικές στο Test Automation;

Επιλέγουμε tests με ξεκάθαρο σκοπό, δίνουμε περιγραφικά ονόματα, ορίζουμε αξιόπιστα assertions και φροντίζουμε κάθε test να μπορεί να εκτελείται ανεξάρτητα. Χρησιμοποιούμε σταθερούς locators, κατάλληλα waits αντί για αυθαίρετα sleep, ελεγχόμενα test data και σαφή reports. Αποφεύγουμε τις επαναλαμβανόμενες υλοποιήσεις και ενσωματώνουμε κρίσιμα tests στο CI/CD. Όταν ένα test αποτυγχάνει, εξετάζουμε αν υπάρχει bug στην εφαρμογή ή πρόβλημα στο ίδιο το test.

Παράδειγμα: Αντί για αναμονή 5 δευτερολέπτων μετά το login, περιμένουμε μέχρι να εμφανιστεί το συγκεκριμένο στοιχείο της σελίδας που επιβεβαιώνει την επιτυχή σύνδεση.

11. Τι είναι η Test Automation Pyramid;

Η Test Automation Pyramid είναι μοντέλο για την ισορροπημένη κατανομή των tests. Στη βάση βρίσκονται πολλά, γρήγορα Unit Tests που ελέγχουν μικρές μονάδες κώδικα. Στη μέση βρίσκονται Integration Tests που επαληθεύουν τη συνεργασία υποσυστημάτων. Στην κορυφή βρίσκονται λιγότερα UI / End-to-End Tests, επειδή συνήθως είναι πιο αργά, πιο δαπανηρά και πιο ευαίσθητα σε αλλαγές. Η πυραμίδα αποτελεί οδηγό, όχι υποχρεωτική αριθμητική αναλογία.

Παράδειγμα: Για μια υπηρεσία παραγγελιών έχουμε πολλά unit tests για τον υπολογισμό τιμών, integration tests για την αποθήκευση παραγγελίας και λίγα end-to-end tests που εκτελούν μια ολόκληρη αγορά από τον browser.

12. Τι σημαίνει Automation Testing;

Automation Testing είναι η χρήση λογισμικού, scripts και εργαλείων για την εκτέλεση δοκιμών με περιορισμένη χειροκίνητη παρέμβαση. Το σύστημα εκτελεί βήματα, συγκρίνει τα πραγματικά αποτελέσματα με τα αναμενόμενα και καταγράφει επιτυχίες ή αποτυχίες. Κύρια οφέλη είναι η επαναληψιμότητα, η ταχύτητα σε συχνούς ελέγχους και η δυνατότητα άμεσης ανατροφοδότησης μετά από αλλαγές. Απαιτεί όμως αρχικό σχεδιασμό και συνεχή συντήρηση.

Παράδειγμα: Σε κάθε push στο GitHub, ένα CI pipeline εκτελεί τα unit και API tests και επισημαίνει αν κάποια αλλαγή έσπασε υπάρχουσα λειτουργία.

13. Ποιοι είναι οι βασικοί τύποι Automated Tests;

Οι τύποι διακρίνονται είτε βάσει επιπέδου ελέγχου είτε βάσει στόχου. Τα Unit Tests ελέγχουν μικρές μονάδες κώδικα. Τα Integration Tests ελέγχουν τη συνεργασία εξαρτήσεων, όπως εφαρμογής και βάσης. Τα UI / GUI Tests ελέγχουν τη διεπαφή και τα End-to-End Tests ολοκληρωμένες ροές χρήστη. Τα Functional Tests ελέγχουν αν μια λειτουργία ανταποκρίνεται στις απαιτήσεις. Τα Smoke Tests επιβεβαιώνουν γρήγορα βασικές λειτουργίες, ενώ τα Regression Tests επαναλαμβάνονται μετά από αλλαγές.

Παράδειγμα: Έλεγχος μιας μεθόδου υπολογισμού ΦΠΑ είναι unit test, έλεγχος ενός REST endpoint μαζί με τη βάση είναι integration test και αγορά προϊόντος μέσω browser είναι end-to-end test.

14. Ποιες πρακτικές πρέπει να ακολουθούμε κατά τη συγγραφή Automated Tests;

Γράφουμε tests ευανάγνωστα, ανεξάρτητα και προβλέψιμα, με σαφή δομή προετοιμασίας, ενέργειας και επαλήθευσης (Arrange–Act–Assert ή Given–When–Then). Χρησιμοποιούμε κοινές βοηθητικές μεθόδους για επαναλαμβανόμενες ενέργειες, αλλά χωρίς υπερβολική αφαίρεση. Τα tests πρέπει να αφήνουν το περιβάλλον καθαρό, να χρησιμοποιούν κατάλληλα δεδομένα και να αποφεύγουν εξαρτήσεις από τη σειρά εκτέλεσης.

Παράδειγμα: Ένα test δημιουργεί δικό του δοκιμαστικό χρήστη, ελέγχει την αλλαγή email και μετά καθαρίζει τα δοκιμαστικά δεδομένα, ώστε να μην επηρεάζει άλλα tests.

15. Τι είναι ένα Automation Testing Framework;

Ένα Automation Testing Framework είναι μια οργανωμένη δομή από βιβλιοθήκες, κανόνες, βοηθητικές λειτουργίες και συμβάσεις που διευκολύνει τη δημιουργία, εκτέλεση και συντήρηση αυτοματοποιημένων tests. Μπορεί να περιλαμβάνει test runners, assertions, διαχείριση test data, κοινά components, configuration και reporting. Το framework δεν είναι πάντα ένα μοναδικό προϊόν· μπορεί να αποτελεί συνδυασμό εργαλείων.

Παράδειγμα: Μια ομάδα δημιουργεί framework σε Java χρησιμοποιώντας Selenium για browser actions, JUnit για εκτέλεση και assertions και Maven για διαχείριση του project.

16. Ποια πλεονεκτήματα προσφέρουν τα Automation Testing Frameworks;

Τα frameworks προσφέρουν ομοιομορφία στον τρόπο συγγραφής των tests, επαναχρησιμοποίηση κοινών λειτουργιών, ευκολότερη συντήρηση και δυνατότητα επέκτασης της test suite. Μπορούν επίσης να κεντρικοποιήσουν τη διαχείριση browsers, δεδομένων, configuration και αναφορών, ώστε οι testers να επικεντρώνονται στη συμπεριφορά της εφαρμογής. Το όφελος εξαρτάται από το πόσο σωστά έχει σχεδιαστεί η δομή.

Παράδειγμα: Αν αλλάξει το πεδίο του username στη σελίδα σύνδεσης, διορθώνουμε μία κοινή μέθοδο ή έναν page object αντί να αλλάξουμε 50 διαφορετικά tests.

17. Ποια είδη Automation Testing Frameworks υπάρχουν;

Στο Data-Driven Testing, το ίδιο test εκτελείται με διαφορετικά δεδομένα. Στο Modular Testing, η λειτουργικότητα χωρίζεται σε επαναχρησιμοποιήσιμες μονάδες. Το Keyword-Driven Testing οργανώνει τις ενέργειες σε keywords, όπως Open Browser ή Login. Το Hybrid Testing συνδυάζει προσεγγίσεις. Το Model-Based Testing δημιουργεί ή καθοδηγεί tests βάσει μοντέλου της εφαρμογής. Το Code-Driven Testing βασίζεται σε προγραμματιστικό κώδικα, ενώ το BDD περιγράφει αναμενόμενη συμπεριφορά με σενάρια κατανοητά και από μη προγραμματιστές. Αυτές οι κατηγορίες μπορούν να συνυπάρχουν.

Παράδειγμα: Ένα login test διαβάζει 10 συνδυασμούς credentials από CSV (data-driven) και χρησιμοποιεί κοινό keyword Login As User (keyword-driven).

18. Ποιες περιπτώσεις είναι κατάλληλες και ποιες ακατάλληλες για Automation Testing;

Κατάλληλες περιπτώσεις είναι οι επαναλαμβανόμενοι έλεγχοι, τα σταθερά regression scenarios, οι δοκιμές με πολλά σύνολα δεδομένων και οι έλεγχοι που πρέπει να τρέχουν σε κάθε build. Λιγότερο κατάλληλες είναι οι μοναδικές δοκιμές, οι ασταθείς ή ταχέως μεταβαλλόμενες λειτουργίες και οι δραστηριότητες που απαιτούν διερευνητική ή αισθητική κρίση. Η απόφαση βασίζεται στην αναμενόμενη αξία, στον κίνδυνο, στη συχνότητα και στο κόστος συντήρησης (ROI).

Παράδειγμα: Οι 100 συνδυασμοί ορίων μιας φόρμας είναι καλοί υποψήφιοι για data-driven automation, ενώ η πρώτη αξιολόγηση του σχεδιασμού της φόρμας είναι συνήθως καλύτερα να γίνει χειροκίνητα.

19. Πώς μετράμε την επιτυχία του Automation Testing;

Η επιτυχία δεν μετριέται μόνο από τον αριθμό των scripts. Αξιολογούμε τη χρονική εξοικονόμηση, την ταχύτητα ανατροφοδότησης μετά από αλλαγές, τη σταθερότητα των tests (flaky tests), το κόστος ανάπτυξης και συντήρησης, τον χρόνο διάγνωσης αποτυχιών και την κάλυψη σημαντικών λειτουργικών κινδύνων. Το Test Coverage είναι χρήσιμο, αλλά υψηλή κάλυψη δεν εγγυάται υψηλή ποιότητα των assertions ή απουσία bugs.

Παράδειγμα: Αν ένα regression suite που απαιτούσε 3 ώρες χειροκίνητα εκτελείται σε 15 λεπτά και βρίσκει έγκαιρα πραγματικά προβλήματα, έχουμε μετρήσιμο όφελος — αρκεί να μην απαιτεί συνεχείς χειροκίνητες διορθώσεις.

20. Ποιες είναι οι διαφορές μεταξύ Manual Testing και Automation Testing;

Στο Manual Testing ένας άνθρωπος εκτελεί και παρατηρεί τους ελέγχους. Είναι ιδιαίτερα χρήσιμο στην εξερεύνηση νέων λειτουργιών, στην αξιολόγηση ευχρηστίας και σε απρόβλεπτα σενάρια. Στο Automation Testing τα tests εκτελούνται από κώδικα ή εργαλεία, προσφέροντας ταχύτητα και συνέπεια σε επαναλήψεις, αλλά απαιτώντας χρόνο για ανάπτυξη, συντήρηση και υποδομές. Οι δύο προσεγγίσεις δεν είναι ανταγωνιστικές· καλύπτουν διαφορετικές ανάγκες.

Παράδειγμα: Ένας tester εξερευνά χειροκίνητα μια νέα διαδικασία checkout και, αφού σταθεροποιηθεί, αυτοματοποιεί τις βασικές περιπτώσεις επιτυχούς και αποτυχημένης αγοράς.

21. Μπορεί το Automation Testing να αντικαταστήσει το Manual Testing;

Όχι πλήρως. Η αυτοματοποίηση μπορεί να αναλάβει μεγάλο αριθμό επαναλαμβανόμενων ελέγχων, όμως η ανθρώπινη κρίση παραμένει απαραίτητη για διερευνητικό έλεγχο, αξιολόγηση ευχρηστίας και κατανόηση απρόβλεπτης συμπεριφοράς. Επιπλέον, κάποιος πρέπει να επιλέγει σωστά τα σενάρια, να διαβάζει τα αποτελέσματα και να ερευνά τις αποτυχίες των tests.

Παράδειγμα: Ένα αυτοματοποιημένο test επιβεβαιώνει ότι εμφανίζεται μήνυμα επιτυχίας, αλλά ένας άνθρωπος μπορεί να παρατηρήσει ότι το μήνυμα είναι δυσνόητο ή τοποθετημένο σε λάθος σημείο της οθόνης.

22. Ποια είναι τα βασικά βήματα του κύκλου ζωής του Automation Testing;

Ξεκινάμε με ανάλυση απαιτήσεων και στόχων, καθορισμό των test cases που έχουν αξία για αυτοματοποίηση και επιλογή κατάλληλων εργαλείων. Στη συνέχεια προετοιμάζουμε το περιβάλλον και τα δεδομένα, σχεδιάζουμε το framework, υλοποιούμε scripts με assertions και εκτελούμε τα tests. Τέλος, αναλύουμε τα reports, καταγράφουμε bugs και συντηρούμε τα tests καθώς η εφαρμογή εξελίσσεται. Η διαδικασία είναι επαναληπτική, όχι κάτι που γίνεται μία φορά.

Παράδειγμα: Για ένα API εγγραφής χρήστη ορίζουμε απαιτήσεις, δημιουργούμε σενάρια έγκυρων και άκυρων δεδομένων, τα ενσωματώνουμε στο CI και ενημερώνουμε τα tests όταν αλλάξει η προδιαγραφή.

23. Ποια είναι μερικά από τα πιο δημοφιλή Automation Testing Tools;

Ενδεικτικά εργαλεία είναι το Selenium για web browser automation, το Appium για mobile εφαρμογές, το UFT, το Ranorex και το Tricentis Tosca για διαφορετικές ανάγκες επιχειρησιακής αυτοματοποίησης, καθώς και το SoapUI για API testing. Υπάρχουν επίσης σύγχρονες επιλογές όπως Playwright και Cypress για web testing. Κάθε εργαλείο έχει διαφορετικό πεδίο εφαρμογής, τρόπο ανάπτυξης, κόστος και υποστήριξη.

Παράδειγμα: Για native Android εφαρμογή εξετάζουμε Appium, ενώ για web UI tests μπορεί να επιλεγεί Selenium ή Playwright.

24. Πώς επιλέγουμε το κατάλληλο Automation Testing Tool;

Πρώτα ορίζουμε τι θέλουμε να δοκιμάσουμε: web UI, mobile, API ή πολλαπλά επίπεδα. Έπειτα εξετάζουμε τη συμβατότητα με τις τεχνολογίες μας, τις δεξιότητες της ομάδας, τη δυνατότητα CI/CD, τα reports, τη συντήρηση, την κλιμάκωση και το συνολικό κόστος. Είναι χρήσιμο να υλοποιήσουμε ένα μικρό Proof of Concept (PoC) πριν δεσμευτούμε σε ένα εργαλείο.

Παράδειγμα: Δύο εργαλεία μπορεί να υποστηρίζουν τον ίδιο browser, αλλά το ένα να συνεργάζεται καλύτερα με την υπάρχουσα Java test suite και το άλλο με την ομάδα JavaScript.

25. Είναι εφικτό να αυτοματοποιήσουμε το 100% των tests;

Στην πράξη σπάνια είναι επιθυμητό ή οικονομικά αποδοτικό. Πολλές λειτουργικές απαιτήσεις μπορούν να ελεγχθούν αυτόματα, αλλά υπάρχουν περιπτώσεις που χρειάζονται ανθρώπινη κρίση, όπως η χρηστικότητα, η αισθητική ή η διερευνητική αξιολόγηση. Επιπλέον, η πλήρης κάλυψη όλων των πιθανών δεδομένων και συνδυασμών συχνά δεν είναι εφικτή. Στόχος είναι να αυτοματοποιούμε τους ελέγχους με τη μεγαλύτερη αξία και τον μεγαλύτερο κίνδυνο.

Παράδειγμα: Αυτοματοποιούμε τον έλεγχο των υποχρεωτικών πεδίων μιας φόρμας, αλλά η συνολική ευκολία συμπλήρωσής της αξιολογείται και από πραγματικούς χρήστες.

26. Ποιος είναι υπεύθυνος για το Test Automation, οι Developers ή η ομάδα QA;

Η ποιότητα είναι κοινή ευθύνη. Οι developers συνήθως αναλαμβάνουν σημαντικό μέρος των unit και integration tests και βοηθούν στη δημιουργία εφαρμογών που δοκιμάζονται εύκολα. Οι QA engineers σχεδιάζουν στρατηγική ελέγχων, εντοπίζουν κρίσιμα σενάρια, υλοποιούν κατάλληλα automated tests και εξετάζουν την ποιότητα από την πλευρά του χρήστη. Η συνεργασία με DevOps ή platform engineers βοηθά στην αξιόπιστη εκτέλεση των tests στο CI/CD.

Παράδειγμα: Ο developer γράφει unit tests για έναν υπολογισμό έκπτωσης και ο QA engineer προσθέτει end-to-end test για την εφαρμογή της έκπτωσης στο checkout.

27. Τι είναι το Selenium και ποια είναι τα πλεονεκτήματα και τα μειονεκτήματά του;

Το Selenium είναι ένα σύνολο open-source εργαλείων για τον αυτοματισμό web browsers. Πλεονεκτήματα είναι η υποστήριξη πολλών browsers, γλωσσών προγραμματισμού και λειτουργικών συστημάτων, καθώς και η μεγάλη κοινότητα και το οικοσύστημα βιβλιοθηκών. Μειονεκτήματα είναι η ανάγκη προγραμματιστικών γνώσεων, η ευαισθησία κακοσχεδιασμένων UI tests σε αλλαγές της σελίδας και το γεγονός ότι η καταγραφή reports ή η οργάνωση tests απαιτεί συχνά πρόσθετα εργαλεία. Το Selenium αφορά κυρίως web browser automation, όχι γενική αυτοματοποίηση κάθε desktop εφαρμογής.

Παράδειγμα: Με Selenium WebDriver σε Java μπορούμε να ανοίξουμε μια σελίδα login, να συμπληρώσουμε πεδία και να επιβεβαιώσουμε ότι ο χρήστης συνδέθηκε.

28. Ποια είναι τα βασικά συστατικά του Selenium;

Το Selenium WebDriver παρέχει API για προγραμματιστικό έλεγχο του browser, όπως εντοπισμό στοιχείων, clicks και ανάγνωση περιεχομένου. Το Selenium Grid επιτρέπει την εκτέλεση browser tests σε πολλαπλά περιβάλλοντα, συχνά απομακρυσμένα ή παράλληλα. Το Selenium IDE προσφέρει γραφικό περιβάλλον για καταγραφή και αναπαραγωγή ενεργειών, χρήσιμο κυρίως για απλούστερα σενάρια και πειραματισμό.

Παράδειγμα: Γράφουμε το test με WebDriver, το εκτελούμε στον Chrome και στον Firefox μέσω Grid και χρησιμοποιούμε IDE για μια γρήγορη καταγραφή απλής ροής.

29. Τι είναι το UI Testing;

Το User Interface (UI) Testing ελέγχει τα ορατά στοιχεία μιας εφαρμογής και τη συμπεριφορά τους: κουμπιά, πεδία, μενού, φόρμες, μηνύματα και πλοήγηση. Περιλαμβάνει λειτουργικές επαληθεύσεις, ενώ μπορεί να συνδυάζεται με ελέγχους εμφάνισης, responsive design και προσβασιμότητας. Η αυτόματη επιβεβαίωση ενός στοιχείου δεν αρκεί πάντα για να αξιολογηθεί η συνολική εμπειρία χρήσης.

Παράδειγμα: Πατάμε το κουμπί «Αποθήκευση», ελέγχουμε ότι εμφανίζεται μήνυμα επιτυχίας και επιβεβαιώνουμε ότι οι αλλαγές παραμένουν μετά από ανανέωση της σελίδας.

30. Τι είναι το Protractor;

Το Protractor ήταν open-source framework για End-to-End Testing web εφαρμογών, ιδιαίτερα εφαρμογών Angular. Βασιζόταν στο Selenium WebDriver και παρείχε ευκολίες για τον χειρισμό χαρακτηριστικών του Angular. Το project έχει τερματίσει την ενεργή ανάπτυξή του (end of life), επομένως δεν αποτελεί συνήθως κατάλληλη επιλογή για νέα projects. Σε παλιότερες εφαρμογές μπορεί να το συναντήσουμε σε υφιστάμενες test suites.

Παράδειγμα: Μια παλιά Angular εφαρμογή μπορεί να έχει tests Protractor που ελέγχουν τη δημιουργία και την επεξεργασία εγγραφών. Κατά τον εκσυγχρονισμό της, η ομάδα μπορεί να εξετάσει μετάβαση σε Playwright ή Cypress.

31. Τι είναι μια Test Automation Platform;

Μια Test Automation Platform είναι ένα πιο ολοκληρωμένο σύστημα για την οργάνωση, εκτέλεση, παρακολούθηση και συχνά τη συντήρηση αυτοματοποιημένων ελέγχων. Μπορεί να συνδυάζει test cases, scripts, επιλογή περιβάλλοντος, test data, προγραμματισμένες εκτελέσεις, διαχείριση αποτελεσμάτων και reports. Διαφέρει από μια μεμονωμένη βιβλιοθήκη αυτοματοποίησης, επειδή προσφέρει ευρύτερες δυνατότητες διαχείρισης.

Παράδειγμα: Μια πλατφόρμα μπορεί να επιτρέπει σε tester να επιλέγει περιβάλλον, να εκκινεί ένα test suite και να βλέπει συγκεντρωτικά ποια tests πέτυχαν ή απέτυχαν, με logs για κάθε εκτέλεση.

32. Ποιες είναι μερικές εναλλακτικές λύσεις του Selenium;

Για web browser testing υπάρχουν εργαλεία όπως Playwright και Cypress, που προσφέρουν διαφορετικές προσεγγίσεις στην εκτέλεση UI tests. Το Robot Framework είναι keyword-driven framework που μπορεί να χρησιμοποιεί browser libraries. Το Cucumber είναι εργαλείο υποστήριξης BDD και μπορεί να συνδυαστεί με Selenium ή άλλους browser drivers· δεν αποτελεί από μόνο του ισοδύναμο browser automation engine. Επομένως, συγκρίνουμε εργαλεία ανάλογα με τον πραγματικό τους ρόλο.

Παράδειγμα: Μια ομάδα μπορεί να επιλέξει Playwright για browser automation ή Selenium μαζί με Cucumber ώστε να γράφει σενάρια Given–When–Then.

33. Τι είναι το Robot Framework και ποια είναι η βασική αρχιτεκτονική του;

Το Robot Framework είναι open-source framework για Acceptance Testing, αυτοματοποιημένες δοκιμές και Robotic Process Automation (RPA). Είναι υλοποιημένο σε Python, αλλά μπορεί να ελέγχει συστήματα με διαφορετικές τεχνολογίες μέσω βιβλιοθηκών. Οργανώνει τα tests σε Test Suites και χρησιμοποιεί keywords, τα οποία μπορεί να είναι ενσωματωμένα, να προέρχονται από libraries ή να δημιουργούνται από την ομάδα. Παρέχει επίσης logs και reports.

Παράδειγμα: Ένα σενάριο μπορεί να περιλαμβάνει keywords Open Browser, Input Text, Click Button και Page Should Contain, χωρίς ο συντάκτης να γράφει απαραίτητα τον χαμηλού επιπέδου κώδικα κάθε ενέργειας.

34. Ποια Test Library APIs προσφέρει το Robot Framework;

Το Static API εκθέτει keywords από γνωστές μεθόδους ή συναρτήσεις μιας βιβλιοθήκης. Το Dynamic API επιτρέπει στη βιβλιοθήκη να δηλώνει προγραμματιστικά ποια keywords υποστηρίζει και πώς εκτελούνται. Το Hybrid API συνδυάζει τη δυναμική δήλωση των διαθέσιμων keywords με πιο στατική υλοποίηση της εκτέλεσής τους. Η επιλογή εξαρτάται από το αν τα keywords είναι σταθερά ή πρέπει να αλλάζουν ανάλογα με την κατάσταση.

Παράδειγμα: Μια απλή library με μέθοδο login_user() μπορεί να χρησιμοποιεί Static API, ενώ μια library που δημιουργεί keywords από εξωτερικό configuration μπορεί να ωφεληθεί από Dynamic API.

35. Πώς αυτοματοποιούμε τη λειτουργία Login μιας web εφαρμογής;

Αρχικά μελετάμε τη φόρμα και τις απαιτήσεις της: έγκυρα και άκυρα στοιχεία, υποχρεωτικά πεδία, μηνύματα σφάλματος, ανακατευθύνσεις και χειρισμό συνεδρίας. Στη συνέχεια δημιουργούμε test cases με σαφή αναμενόμενα αποτελέσματα, εξασφαλίζουμε δοκιμαστικούς χρήστες και υλοποιούμε το σενάριο με αξιόπιστους locators και waits. Τέλος, επιβεβαιώνουμε την έκβαση με assertions και καθαρίζουμε την κατάσταση μεταξύ των tests. Δεν αποθηκεύουμε πραγματικά passwords μέσα στον κώδικα.

Παράδειγμα: Με σωστά credentials αναμένουμε μετάβαση στο dashboard. Με λανθασμένο password αναμένουμε μήνυμα σφάλματος και παραμονή στη φόρμα, χωρίς να δημιουργηθεί authenticated session.

36. Ποιοι είναι οι βασικοί κίνδυνοι του Automated Testing;

Κίνδυνοι είναι το υψηλό αρχικό και διαρκές κόστος, το αρνητικό ROI όταν επιλέγονται ακατάλληλα tests, η εξάρτηση από συγκεκριμένα εργαλεία, οι αλλαγές της εφαρμογής που σπάνε scripts και τα flaky tests που αποτυγχάνουν περιστασιακά χωρίς πραγματικό bug. Επίσης, η υπερβολική εμπιστοσύνη σε μια test suite μπορεί να δημιουργήσει ψευδή αίσθηση ασφάλειας, ιδίως όταν λείπουν κρίσιμα σενάρια.

Παράδειγμα: Ένα UI test που βασίζεται σε σταθερό sleep(2) μπορεί να αποτυγχάνει σε αργό CI server, παρότι η εφαρμογή λειτουργεί σωστά. Η λύση είναι καλύτερη αναμονή και σταθερότερο test design.

37. Ποιες είναι οι φάσεις του Automation Testing Life Cycle;

Οι βασικές φάσεις είναι: (1) ορισμός scope και στόχων, (2) αξιολόγηση και επιλογή εργαλείων, (3) σχεδιασμός στρατηγικής και Test Plan, (4) προετοιμασία Test Environment και test data, (5) ανάπτυξη framework και scripts, (6) εκτέλεση των tests, (7) ανάλυση αποτελεσμάτων και reporting και (8) συντήρηση και βελτίωση της test suite. Ο κύκλος επαναλαμβάνεται όταν αλλάζει η εφαρμογή ή οι απαιτήσεις.

Παράδειγμα: Πριν αυτοματοποιήσουμε μια λειτουργία αναζήτησης, καθορίζουμε τις αναμενόμενες συμπεριφορές, φτιάχνουμε δεδομένα, υλοποιούμε ελέγχους και τους εκτελούμε σε κάθε νέα έκδοση.

38. Τι είναι το CAPTCHA;

Το CAPTCHA προέρχεται από το Completely Automated Public Turing Test to Tell Computers and Humans Apart. Είναι μηχανισμός που προσπαθεί να διακρίνει έναν πραγματικό χρήστη από αυτοματοποιημένη δραστηριότητα και να περιορίσει ενέργειες όπως spam ή κατάχρηση φόρμας. Δεν προσφέρει απόλυτη προστασία και συχνά αποτελεί μέρος μιας ευρύτερης στρατηγικής ασφαλείας.

Παράδειγμα: Μια φόρμα εγγραφής μπορεί να ζητά επιπλέον επιβεβαίωση πριν δημιουργηθεί λογαριασμός, όταν το σύστημα εντοπίζει ύποπτη δραστηριότητα.

39. Πώς αυτοματοποιούμε το Testing ενός CAPTCHA;

Στα αυτοματοποιημένα tests δεν προσπαθούμε συνήθως να λύσουμε το πραγματικό CAPTCHA. Αντίθετα, χρησιμοποιούμε τις επίσημες test keys, ένα test mode ή κατάλληλο mock/stub της υπηρεσίας CAPTCHA σε ελεγχόμενο περιβάλλον. Έτσι ελέγχουμε τη συμπεριφορά της εφαρμογής όταν η επαλήθευση επιστρέφει επιτυχία, αποτυχία ή τεχνικό σφάλμα, χωρίς να παρακάμπτουμε μηχανισμούς ασφαλείας στο production.

Παράδειγμα: Σε test environment προσομοιώνουμε απάντηση «verified» και ελέγχουμε ότι επιτρέπεται η υποβολή της φόρμας. Έπειτα προσομοιώνουμε «rejected» και ελέγχουμε ότι η υποβολή απορρίπτεται με κατάλληλο μήνυμα.

40. Ποιες πρακτικές ανάπτυξης πρέπει να ακολουθούμε όταν γράφουμε Automated Tests;

Ακολουθούμε τις γενικές αρχές καθαρού και συντηρήσιμου κώδικα: μικρά tests με συγκεκριμένο στόχο, συνεπή ονόματα, αποφυγή διπλοτυπίας, διαχωρισμό test logic από βοηθητικές λειτουργίες, κατάλληλη διαχείριση σφαλμάτων και εκτέλεση σε σταθερό περιβάλλον. Δεν δημιουργούμε tests που εξαρτώνται από άλλα tests ή από μη ελεγχόμενα δεδομένα. Κάνουμε code review στα tests, όπως και στον κώδικα της εφαρμογής.

Παράδειγμα: Αν 20 tests χρειάζονται login, δημιουργούμε κοινή βοηθητική λειτουργία ή κατάλληλο fixture αντί να αντιγράφουμε τον ίδιο κώδικα 20 φορές. Αν αλλάξει η διαδικασία σύνδεσης, ενημερώνουμε ένα σημείο.
