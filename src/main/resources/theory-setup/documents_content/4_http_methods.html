HTTP Methods – Semantics και Idempotency

Χρήσιμος σύνδεσμος αναφοράς:

http.dev/methods

1. Βασικές HTTP Methods

Οι βασικές HTTP methods που θα εξετάσουμε είναι: GET, POST, PUT, PATCH, DELETE, OPTIONS, HEAD

2. Η βασική ιδέα: Semantics vs Implementation

Κάθε HTTP method κουβαλάει συγκεκριμένη σημασιολογία (semantics). Η method δηλώνει την πρόθεση του request — τι θέλουμε να πετύχουμε — αλλά δεν γράφει από μόνη της το business logic.

HTTP Request ↓ Controller ↓ Service ↓ Repository ↓ Database

Η HTTP method δηλώνει το contract / intention. Ο δικός μας κώδικας καθορίζει τι θα γίνει πραγματικά.

Άρα τεχνικά μπορούμε να γράψουμε PUT που κάνει partial update, PATCH που κάνει full replacement ή POST που κάνει update. Ο κώδικας μπορεί να λειτουργεί, αλλά τότε η υλοποίηση δεν ακολουθεί σωστά τη σημασιολογία της method.

3. POST

Η POST χρησιμοποιείται κυρίως για δημιουργία νέου resource, εκτέλεση κάποιας ενέργειας, αποστολή δεδομένων προς επεξεργασία ή σύνθετη αναζήτηση.

• Μπορεί να έχει body.

• Μπορεί να έχει path params.

• Μπορεί να έχει query params.

• Το body δεν είναι υποχρεωτικό.

• Δεν έχει idempotent semantics: το ίδιο request μπορεί να έχει νέο effect κάθε φορά.

POST → «Πάρε αυτά τα δεδομένα και επεξεργάσου τα σύμφωνα με τη λειτουργία αυτού του endpoint.»

4. GET

Η GET χρησιμοποιείται για ανάκτηση δεδομένων.

• Στο REST API design που εξετάζουμε δεν χρησιμοποιούμε body.

• Μπορεί να έχει path params.

• Μπορεί να έχει query params.

• Είναι idempotent.

• Η πρόθεσή της είναι read, όχι modification.

GET → «Θέλω να διαβάσω δεδομένα.»

5. PUT

Η PUT δηλώνει πλήρη αντικατάσταση / ορισμό της κατάστασης ενός συγκεκριμένου resource. Συνήθως στέλνουμε ολόκληρη τη νέα representation.

• Μπορεί να έχει body.

• Μπορεί να έχει path params.

• Μπορεί να έχει query params.

• Έχει idempotent semantics.

• Αν την υλοποιήσουμε non-idempotently, παραβιάζουμε τη σημασιολογία της PUT.

PUT → «Κάνε αυτό το resource να έχει αυτή την κατάσταση.»

6. PATCH

Η PATCH δηλώνει μερική τροποποίηση ενός υπάρχοντος resource.

• Μπορεί να έχει body.

• Μπορεί να έχει path params.

• Μπορεί να έχει query params.

• Δεν εγγυάται idempotency.

• Ένα συγκεκριμένο PATCH μπορεί να είναι idempotent ή non-idempotent ανάλογα με την operation.

PATCH → «Κάνε αυτές τις συγκεκριμένες αλλαγές στο υπάρχον resource.»

7. DELETE

Η DELETE δηλώνει διαγραφή ενός resource. Στα παραδείγματά μας θα εντοπίζουμε τον user με email.

• Το resource μπορεί να εντοπιστεί με id, email ή άλλο identifier.

• Είναι idempotent ως προς το intended final state.

DELETE → «Διέγραψε αυτό το resource.»

8. OPTIONS

Η OPTIONS χρησιμοποιείται για να μάθουμε ποιες HTTP methods ή δυνατότητες υποστηρίζει ένα endpoint. Χρησιμοποιείται επίσης σε CORS preflight requests.

• Επιστρέφει πληροφορίες για supported capabilities/methods.

• Είναι idempotent.

OPTIONS → «Τι επιτρέπεται / τι υποστηρίζεται εδώ;»

9. HEAD

Η HEAD χρησιμοποιείται όταν θέλουμε να πάρουμε μόνο τα response headers, χωρίς response body.

• Δεν επιστρέφει response body.

• Μπορεί να μας δώσει Content-Type, Content-Length, ETag, Last-Modified κ.ά.

• Είναι idempotent.

HEAD → «Δώσε μου τα metadata / headers της response χωρίς το body.»

10. Κοινό Παράδειγμα – Users API

Έστω ότι στη βάση υπάρχει ο παρακάτω user:

{ "id": 15, "username": "nikos", "email": "nikos@test.com", "age": 30, "active": true }

10.1 POST – Δημιουργία User

POST /users Content-Type: application/json

{ "username": "maria", "email": "maria@test.com", "age": 25, "active": true }

Ο server μπορεί να δημιουργήσει:

{ "id": 16, "username": "maria", "email": "maria@test.com", "age": 25, "active": true }

Αν ξαναστείλουμε το ίδιο POST σε ένα απλό create endpoint χωρίς προστασία από duplicates, μπορεί να δημιουργηθεί νέα εγγραφή με νέο id. Αυτό είναι χαρακτηριστικό παράδειγμα non-idempotent συμπεριφοράς.

1ο ίδιο POST → user id = 16 2ο ίδιο POST → user id = 17 3ο ίδιο POST → user id = 18

10.2 POST – Αναζήτηση με Body και Query Params

POST /users/search?page=0&size=10&sort=username Content-Type: application/json

{ "active": true, "minAge": 20, "maxAge": 40 }

Εδώ το body περιέχει τα search criteria, ενώ τα query params χρησιμοποιούνται για pagination και sorting.

10.3 GET – User με Email

GET /users?email=nikos@test.com

Το email περνάει ως query parameter. Δεν χρησιμοποιούμε request body.

{ "id": 15, "username": "nikos", "email": "nikos@test.com", "age": 30, "active": true }

10.4 PUT – Πλήρης Αντικατάσταση User

PUT /users/15 Content-Type: application/json

{ "username": "nikos", "email": "newemail@test.com", "age": 30, "active": true }

Η πρόθεση είναι να οριστεί η νέα πλήρης κατάσταση του resource /users/15.

10.5 Naive PUT – Τι γίνεται αν στείλουμε μόνο email;

PUT /users/15 Content-Type: application/json

{ "email": "newemail@test.com" }

Σε μία απλή Spring Boot/JPA υλοποίηση όπου κάνουμε bind το body κατευθείαν σε User και μετά save(), τα fields που δεν στάλθηκαν μπορούν να είναι null στο Java object.

@PutMapping("/{id}") public User updateUser(@PathVariable Long id, @RequestBody User user) { user.setId(id); return userService.updateUser(user); }

public User updateUser(User user) { return userRepository.save(user); }

id = 15 username = null email = "newemail@test.com" age = null active = null

Αυτά τα null values μπορούν να περάσουν στη βάση, ανάλογα με το mapping και τους database constraints. Το PUT δεν έκανε μόνο του τα fields null· αυτό είναι αποτέλεσμα της συγκεκριμένης implementation.

10.6 Μπορούμε να κάνουμε PUT σαν Partial Update;

public User updateUser(Long id, User request) { User existing = userRepository.findById(id).orElseThrow(); if (request.getEmail() != null) { existing.setEmail(request.getEmail()); } return userRepository.save(existing); }

Ναι. Τεχνικά δουλεύει. Όμως αυτή η συμπεριφορά μοιάζει πλέον με PATCH και δεν εκφράζει σωστά τη σημασιολογία του PUT.

10.7 PATCH – Μερική Ενημέρωση User

PATCH /users/15 Content-Type: application/json

{ "email": "newemail@test.com" }

Η πρόθεση του PATCH είναι να αλλάξει μόνο το email και να κρατήσει τα υπόλοιπα fields όπως είναι.

{ "id": 15, "username": "nikos", "email": "newemail@test.com", "age": 30, "active": true }

10.8 Σημαντικό – Το @PatchMapping δεν κάνει μόνο του Partial Update

@PatchMapping("/{id}") public User patchUser(@PathVariable Long id, @RequestBody User user) { user.setId(id); return userService.updateUser(user); }

public User updateUser(User user) { return userRepository.save(user); }

Αν στείλουμε μόνο email, το δεσμευμένο User object μπορεί πάλι να έχει null στα υπόλοιπα fields. Άρα ένα naive PATCH μπορεί να έχει το ίδιο πρακτικό πρόβλημα με ένα naive PUT.

Το @PutMapping και το @PatchMapping δεν εφαρμόζουν από μόνα τους διαφορετικό update algorithm. Δηλώνουν διαφορετική HTTP method / semantics. Το update logic το γράφουμε εμείς.

10.9 PATCH Service – Πραγματικό Partial Update

public User patchUser(Long id, User request) { User existing = userRepository.findById(id).orElseThrow(); if (request.getUsername() != null) { existing.setUsername(request.getUsername()); } if (request.getEmail() != null) { existing.setEmail(request.getEmail()); } if (request.getAge() != null) { existing.setAge(request.getAge()); } if (request.getActive() != null) { existing.setActive(request.getActive()); } return userRepository.save(existing); }

Με body μόνο {"email":"newemail@test.com"}, αλλάζει μόνο το email.

10.10 DELETE – User με Email

DELETE /users?email=nikos@test.com

Αν ολοκληρωθεί επιτυχώς, ο user με αυτό το email δεν υπάρχει πλέον. Ένα πιθανό response είναι 204 No Content.

10.11 OPTIONS

OPTIONS /users HTTP/1.1 204 No Content Allow: GET, POST, PUT, PATCH, DELETE, OPTIONS

Το Allow δείχνει ποιες HTTP methods υποστηρίζει το endpoint.

10.12 HEAD

HEAD /users/15 HTTP/1.1 200 OK Content-Type: application/json Content-Length: 104 ETag: "user-15-v4" Last-Modified: Wed, 07 Oct 2026 15:30:00 GMT

Δεν υπάρχει response body. Παίρνουμε μόνο τα response headers.

11. Idempotency – Τι σημαίνει ακριβώς;

Idempotent είναι ένα operation όταν, αν στείλουμε ακριβώς το ίδιο request πολλές φορές, το τελικό state του συστήματος μετά την πρώτη επιτυχημένη εκτέλεση δεν αλλάζει περισσότερο από τις επαναλήψεις.

Idempotency δεν σημαίνει «δημιουργείται ή όχι νέα εγγραφή». Σημαίνει «η επανάληψη του ίδιου request αλλάζει ξανά το final state;»

11.1 SET vs INCREMENT

SET age = 31 1η φορά → 31 2η φορά → 31 10η φορά → 31 => idempotent

INCREMENT age by 1 30 → 31 → 32 → 33 → 34 => non-idempotent

11.2 POST – Non-Idempotent by Semantics

Ένα συνηθισμένο POST create endpoint μπορεί να δημιουργήσει νέα εγγραφή σε κάθε επανάληψη του ίδιου request. Γι’ αυτό η POST δεν εγγυάται idempotency.

POST /users (ίδιο body) 1η φορά → user id 16 2η φορά → user id 17 3η φορά → user id 18

Μπορούμε όμως να γράψουμε συγκεκριμένο POST endpoint που να συμπεριφέρεται idempotently, π.χ. create-or-update με lookup βάσει email:

public User createOrUpdate(User request) { User user = userRepository .findByEmail(request.getEmail()) .orElse(new User()); user.setUsername(request.getUsername()); user.setEmail(request.getEmail()); return userRepository.save(user); }

Το UNIQUE constraint δεν είναι απαραίτητο για να γράψουμε αυτή τη business logic, αλλά μπορεί να προσφέρει επιπλέον προστασία από duplicates στη βάση. Η POST ως HTTP method παραμένει non-idempotent by semantics· απλώς το συγκεκριμένο endpoint μπορεί να έχει idempotent συμπεριφορά.

11.3 PUT – Idempotent by Semantics

PUT /users/15

{ "username": "nikos", "email": "new@test.com", "age": 30, "active": true }

1ο ίδιο PUT → ίδιο final state 2ο ίδιο PUT → ίδιο final state 10ο ίδιο PUT → ίδιο final state

Αν όμως γράψουμε μέσα στο PUT service operation όπως:

user.setAge(user.getAge() + 1);

1ο PUT → 30 → 31 2ο PUT → 31 → 32 3ο PUT → 32 → 33

Τεχνικά μπορούμε να το κάνουμε, αλλά τότε το endpoint είναι non-idempotent και παραβιάζει τη σημασιολογία του PUT.

11.4 PATCH – Μπορεί να είναι Idempotent ή Non-Idempotent

Η PATCH δεν εγγυάται idempotency. Η συμπεριφορά εξαρτάται από το είδος της αλλαγής.

PATCH /users/15

{ "email": "new@test.com" }

SET email = new@test.com 1η φορά → new@test.com 10η φορά → new@test.com => αυτό το operation είναι idempotent

PATCH /users/15

{ "operation": "increaseAge", "value": 1 }

30 → 31 → 32 → 33 => αυτό το operation είναι non-idempotent

11.5 DELETE – Idempotent

DELETE /users?email=nikos@test.com

1η φορά → ο user διαγράφεται 2η φορά → ο user εξακολουθεί να μην υπάρχει

Το response μπορεί να διαφέρει (π.χ. 204 την πρώτη φορά και 404 τη δεύτερη), αλλά το intended final state παραμένει ίδιο: ο user δεν υπάρχει.

12. Τελικό Mental Model

GET → Read → Idempotent POST → Create / Action / Process → Δεν εγγυάται idempotency PUT → Replace / Set state → Idempotent by semantics PATCH → Partial modification → Μπορεί να είναι idempotent ή όχι DELETE → Delete → Idempotent OPTIONS → Supported capabilities → Idempotent HEAD → Response headers → Idempotent

Η HTTP method μας λέει τι σημαίνει ότι ζητάμε να γίνει. Ο controller/service/repository κώδικας καθορίζει τι θα γίνει πραγματικά.

Σε ένα σωστά σχεδιασμένο API θέλουμε η συμπεριφορά του endpoint να συμφωνεί με τη σημασιολογία της HTTP method που επιλέξαμε.
